# Running the IDS on a real network

This is the demo guide: how to show the IDS detecting live attacks between two
machines, and how to reproduce every headline detection offline without any
hardware. It has two parts:

- **Offline replay** - no second machine, no network, no privileges. Runs the
  committed captures in [`demo/`](../demo/) through the pipeline and confirms
  each fires. Use this for a laptop demo or CI.
- **Live two-machine demo** - an *attacker* host and a *victim/sensor* host on
  an isolated network. The sensor runs this IDS; the attacker runs the scripts
  in [`scripts/attacks/`](../scripts/attacks/). This is what a marker or an
  audience watches in real time.

Everything that needs two machines is scripted and documented here so a person
can set it up and run it; nothing in this repo attacks anything by itself.

---

## 1. Offline replay (no second machine)

```sh
make build                 # builds bin/ids (needs libpcap-dev)
demo/replay.sh             # replay every capture, print a PASS/FAIL table
demo/replay.sh --list      # list the captures and their headline sid
demo/replay.sh -v          # also print each capture's alerts
demo/replay.sh --dashboard 29   # watch capture 29 in the live TUI (press i, q)
```

`demo/replay.sh` runs each file in [`demo/captures/`](../demo/captures/) through
`ids run -r <file> -rules rules.conf` and checks that the expected alert or
incident appears. A pcap replay needs no capabilities, so a plain `go build`
binary works. The captures are small (< 1 MiB each) and were generated by the
same scenario generators the test suite asserts on, so they are a faithful
stand-in for the live attacks.

Representative output for a report lives in [`demo/output/`](../demo/output/)
(alert log excerpt, dashboard captures, `ids query` examples). Regenerate it
with `demo/make-output.sh`.

The offline replay is enough to *show every detector firing*. The live demo
below adds what a pcap cannot: real capture off the wire, promiscuous mode,
kernel drops under load, and real checksums.

## 2. Why a second machine (and not WSL2)

The IDS runs fine under WSL2 for development and pcap replay, but WSL2 cannot
host a convincing *live* demo:

- **No promiscuous capture of another host.** WSL2's virtual NIC only sees the
  VM's own traffic. Watching one machine attack another needs a real L2 segment
  (a virtual switch between two VMs, or a physical switch with port mirroring).
- **The clock steps.** WSL2's clock can jump when the VM sleeps/resumes. The
  rule engine keys all rate and timing logic on the *packet* timestamp, so a
  pcap is deterministic, but a live capture on a stepping clock produces
  timing artifacts that distract from the demo.
- **Synthetic checksums.** On WSL2 outbound frames carry offloaded (bad)
  L4 checksums and inbound frames arrive coalesced by LRO/GRO, so packet
  counts and checksum-based checks do not reflect the wire. On a proper sensor
  we turn offloads off (below) and see real frames.
- **DNS quirk.** On this project's WSL2 host DNS goes over `lo` to
  `10.255.255.254`, so DNS alerts show that address as both ends. On a real
  segment DNS looks normal.

So the live demo uses two VMs (fast to set up) or two physical hosts (most
realistic). Both are documented below.

## 3. Topology A - two Linux VMs on an isolated network

Two VMs on one host, on a private network with no route to the internet. The
**attacker** runs the scripts; the **victim/sensor** runs the IDS *and* is the
target (so it captures the attack traffic as its own inbound frames).

```
  +-------------------+        isolated L2 segment        +-------------------+
  |   attacker VM     |   192.168.56.0/24 (no gateway)    |  victim / sensor  |
  | 192.168.56.10     |-----------------------------------| 192.168.56.20     |
  | scripts/attacks/  |                                   | bin/ids run -i .. |
  +-------------------+                                   +-------------------+
```

Use static IPs in the RFC 1918 range `192.168.56.0/24`; the attack scripts only
run against private ranges, and this keeps the lab off the internet.

### VirtualBox

1. **Network.** Give both VMs one adapter on the *same* network:
   - *Internal Network* named e.g. `labnet` (fully isolated - recommended), or
   - *Host-only* adapter `vboxnet0` (also reachable from the host).
   - Adapter type: **Intel PRO/1000 MT Desktop (82540EM)** (`e1000`), which
     Linux drives as `enp0s3`/`eth0`.
   - On the **sensor** adapter set **Promiscuous Mode: Allow All** (VM ->
     Settings -> Network -> Advanced). Without this the virtual switch hides
     other stations' frames.
   - CLI equivalent:
     ```sh
     VBoxManage modifyvm attacker --nic1 intnet --intnet1 labnet --nictype1 82540EM
     VBoxManage modifyvm sensor   --nic1 intnet --intnet1 labnet --nictype1 82540EM \
                                  --nicpromisc1 allow-all
     ```
2. **Static addresses** (inside each guest; netplan example):
   ```yaml
   # attacker: /etc/netplan/99-lab.yaml   (sensor: use .20)
   network: {version: 2, ethernets: {enp0s3: {addresses: [192.168.56.10/24]}}}
   ```
   `sudo netplan apply`, then `ping 192.168.56.20` to confirm L2 works.

### libvirt / virt-manager (KVM)

1. Define an **isolated** virtual network (no NAT, no forwarding):
   ```xml
   <!-- labnet.xml:  virsh net-define labnet.xml && virsh net-start labnet -->
   <network>
     <name>labnet</name>
     <bridge name='virbr-lab' stp='on' delay='0'/>
     <!-- no <forward> element => isolated, host-only L2 -->
   </network>
   ```
2. Attach one **virtio** (or `e1000`) NIC on `labnet` to each VM
   (`virt-manager` -> Add Hardware -> Network -> source `labnet`), and set
   static `192.168.56.10` / `.20` inside the guests as above. An isolated
   libvirt bridge already passes all segment traffic to each guest; put the
   sensor NIC in promiscuous mode when you start capture (the IDS does this
   itself).

> **Three-VM SPAN variant.** If you want the sensor to be a *separate* box (not
> the victim), add a third VM on `labnet`, set its adapter Promiscuous Mode to
> *Allow All*, and run the IDS there. On a virtual switch every station on the
> segment then sees the attacker<->victim traffic, which is the software version
> of a mirror port.

Continue at **Section 5 (sensor setup)**.

## 4. Topology B - two physical hosts on a switch

Most realistic, and the only way to show real line-rate behaviour.

```
   attacker ----+                              +---- sensor (bin/ids)
                |     +--------------------+   |
                +-----|  switch (mirror)   |---+
                      |  victim on port 2  |
                      |  mirror -> port 3  |
                      +--------------------+
```

You need the sensor to see the attacker<->victim traffic. Three options, best
first:

1. **Managed switch with port mirroring (SPAN).** Mirror the victim's port to
   the sensor's port. Cisco-style:
   ```
   monitor session 1 source interface Gi0/2 both
   monitor session 1 destination interface Gi0/3
   ```
   The sensor NIC on `Gi0/3` sees a copy of everything to/from the victim.
2. **Network TAP** inline between victim and switch - a copy with no switch
   config, ideal but needs hardware.
3. **Old-style hub** (or a cheap unmanaged switch that floods) - every port
   sees every frame. Simplest for a classroom.

If the sensor is also the victim (attacks aimed straight at it), you need none
of the above - the sensor sees the attack as its own inbound traffic, exactly
like Topology A.

Give all three hosts static addresses on one private subnet, e.g.
`192.168.10.10` (attacker), `.20` (victim), `.30` (sensor).

Continue at **Section 5**.

## 5. Sensor setup

Do this on the machine that runs the IDS.

### 5a. Turn off NIC offloads

Offloads (GRO/LRO coalesce received packets, GSO/TSO batch sends) hide the real
frame boundaries the IDS needs: coalescing merges many packets into one giant
"frame", which distorts packet counts, rate detectors and TCP reassembly. Turn
them off on the capture interface:

```sh
sudo ethtool -K eth0 gro off gso off tso off lro off
```

Confirm they are off (`[fixed]` means the driver never coalesces, which is also
fine):

```sh
ethtool -k eth0 | grep -E \
  'generic-receive-offload|large-receive-offload|tcp-segmentation-offload|generic-segmentation-offload'
# want each: "... : off"   (or "off [fixed]")
```

This is a runtime setting; it resets on reboot or on bringing the link down.

### 5b. Build and grant capture capabilities

```sh
make build          # builds bin/ids and bin/capturedump
make setcap         # runs: sudo setcap cap_net_raw,cap_net_admin=eip on both
```

`make setcap` needs privileges - run it yourself. **Rebuilding strips the
capability**, so re-run `make setcap` after any `make build`. With the
capability set, `bin/ids` captures live without `sudo`.

Verify the capability and that the interface is visible:

```sh
getcap bin/ids                     # -> cap_net_admin,cap_net_raw=eip
bin/capturedump -list              # lists capture interfaces
```

### 5c. Run the sensor with the dashboard

```sh
# full dashboard on the capture interface
bin/ids run -i eth0

# scope with a BPF filter, e.g. only the victim's traffic
bin/ids run -i eth0 -f "host 192.168.56.20"
```

The sensor captures in **promiscuous mode** by default, with a 262144-byte
snaplen (so GRO-sized frames, if any slip through, are not truncated). The
dashboard shows live traffic, alerts and incidents; press `i` to toggle the
incidents panel, `r` to reload rules, `q` to quit. Alerts are also written to
`ids-alerts.jsonl` (change with `-log`).

To capture to a file for later analysis (e.g. to build a new scenario), use the
companion tool:

```sh
bin/capturedump -i eth0 -w /tmp/demo.pcap        # Ctrl-C to stop
```

## 6. Run the attacks (from the attacker host)

On the **attacker** machine, with the sensor already capturing. Every script is
lab-gated: it refuses to run without `--i-have-authorization` and a private
target. See [`scripts/attacks/README.md`](../scripts/attacks/README.md) for the
full table of scripts, required tools, and the sid each triggers.

```sh
# one attack at a time
scripts/attacks/recon.sh       --i-have-authorization -t 192.168.56.20
scripts/attacks/web-attacks.sh --i-have-authorization -t 192.168.56.20 -p 8080

# the whole catalogue, with labels and pauses between steps
scripts/attacks/run-all.sh --i-have-authorization -t 192.168.56.20 -g 192.168.56.1

# just the kill chain: recon -> web exploit -> beacon callback
scripts/attacks/run-all.sh --i-have-authorization -t 192.168.56.20 --kill-chain
```

Some steps need tools on the attacker (`nmap`, `hping3`, `scapy`, `dig`,
`arpspoof`) and some need root there; each script names what it needs and stops
early if it is missing. To give the web and slow-HTTP attacks something to hit,
run any HTTP server on the victim, e.g. `python3 -m http.server 8080`.

Watch the sensor dashboard: recon shows up as scan alerts, the floods as DoS
alerts, the web payloads as HTTP alerts, and `--kill-chain` produces a
**correlated incident** (recon -> exploit -> callback from one source) in the
incidents panel.

## 7. Read the results

```sh
bin/ids query -severity critical           # highest-severity alerts
bin/ids query -kind incident               # correlated incidents
bin/ids query -kind incident -json         # incident detail as JSON
bin/ids query -src 192.168.56.10           # everything from the attacker
bin/ids query -category threat-intel       # feed hits
bin/ids query -since 10m -follow           # tail the log live
```

`bin/ids query` reads the alert log (`-log FILE`, default `ids-alerts.jsonl`).
Credentials (HTTP `Authorization`, FTP `PASS`) are never written to the log or
shown in output.

---

## 8. Cleanup

```sh
# on the attacker: nothing persistent is created by the scripts
# on the sensor: restore offloads if you like (or just reboot)
sudo ethtool -K eth0 gro on gso on tso on lro on
# stop any test HTTP server on the victim (kill it by PID)
```

Tear down the VMs / mirror session when done. The isolated network never had a
route off-host, so nothing leaked.
